## Implementation Summary

Successfully implemented the "Add to Queue" functionality allowing users to queue documents for processing without immediate execution.

### Backend Changes

**File**: `backend/api/routers/text_extraction.py`

1. **Added `queue_only` parameter** to `ExtractionRequest`:
   ```python

       auto_translate: bool = False
       target_languages: Optional[List[str]] = []
       selected_pages: Optional[List[int]] = None
       queue_only: bool = False  # NEW
   ```

## How to Use

### For Users

2. Upload one or more PDF files
3. Configure processing settings (optional)
4. Click "Add to Queue" button
5. View toast notification with queue position

### For Developers

**Backend API Call**:
```javascript
const response = await fetch(`http://localhost:8000/api/text-extraction/extract-with-batching/${documentId}`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({

    queue_only: true,  // Queue without immediate processing

const result = await response.json();
// result.queue_position = 3
// result.estimated_wait_time = 120 (seconds)
```

## Integration with Story 1.5

This story builds on **Story 1.5: Parallel Worker Architecture**:

- 4 concurrent workers process jobs from the queue
- Jobs added via "Add to Queue" go into same queue as "Process Now"
- Both approaches benefit from parallel processing
- Queue depth and position calculated based on worker availability

**Synergy**: Users can now:
1. Upload multiple documents
2. Add all to queue at once
3. Let 4 workers process them concurrently
4. View progress on queue page

## Known Limitations

1. **Queue Position Accuracy**: Currently returns total queue depth, not exact position
   - **Reason**: pgmq doesn't expose message order easily
   - **Impact**: Minor - position is approximate
   - **Future**: Could track in separate table

2. **Wait Time Estimation**: Based on 60 seconds per job average
   - **Reason**: Actual processing time varies by document size
   - **Impact**: Estimate may be inaccurate
   - **Future**: Use historical average from completed jobs

3. **No Priority System**: All queued jobs have same priority
   - **Reason**: pgmq doesn't support priority queues natively
   - **Impact**: Cannot expedite urgent jobs
   - **Future**: Implement priority field in messages
