## User Story

**As a** user working with large PDF documents in the editor,
**I want** PDFs to be cached locally in my browser after first load,
**So that** subsequent editor loads are 10-100x faster and I don't waste time re-downloading the same PDF repeatedly.

---

## Context

### Background

**Problem Identified** (from production usage 2025-10-07):

During production deployment testing, the client observed significant performance issues:
- ✅ PDFs are uploaded through frontend and temporarily held in File objects
- ✅ PDFs are stored in Supabase Storage after upload
- ❌ **Every editor load fetches the entire PDF from Supabase** (slow, wasteful)
- ❌ **Large PDFs (50-150 pages, 5-20 MB) take 3-10 seconds to load** every single time
- ❌ **PDFs never change** during the entire workflow (extraction → translation → complete)
- ❌ **File object is lost** after upload phase (not persisted)

**Current User Experience**:
```
1. User uploads PDF (50 MB, 150 pages)
   → Upload takes 20 seconds (acceptable - one-time operation)

2. User opens Editor (Source Text stage)
   → Fetch from Supabase: 10 seconds ⏳ (SLOW)

3. User clicks "Add to Queue"
   → Returns to Queue page

4. User opens Editor again (Translation stage)
   → Fetch from Supabase: 10 seconds ⏳ (SLOW - SAME PDF!)

5. User switches pages within editor
   → No re-fetch (good)

6. User navigates away and returns to editor
   → Fetch from Supabase: 10 seconds ⏳ (SLOW - AGAIN!)
```

**Expected User Experience with Caching**:
```
1. User uploads PDF (50 MB, 150 pages)
   → Upload takes 20 seconds + Cache in IndexedDB ⚡

2. User opens Editor (Source Text stage)
   → Load from IndexedDB cache: <200ms ⚡⚡⚡ (50x faster!)

3. User navigates away and returns
   → Load from IndexedDB cache: <200ms ⚡⚡⚡ (instant!)

4. User opens editor on different device
   → Fetch from Supabase: 10 seconds (expected - first load on new device)
   → Cache in IndexedDB for future loads ⚡
```

### Technical Context

**Why PDFs Are Perfect for Caching**:
1. **Immutable**: PDFs never change during extraction/translation workflow
2. **Already downloaded**: File is in browser memory during upload phase
3. **Large size**: 5-50 MB files benefit most from caching (avoid network overhead)
4. **Frequent access**: Users open editor multiple times during workflow

**Browser Storage Options**:
- ❌ **LocalStorage**: 5-10 MB limit (too small for PDFs)
- ❌ **SessionStorage**: Cleared on tab close (too short-lived)
- ✅ **IndexedDB**: 50+ MB per origin, persistent, asynchronous (PERFECT for PDFs)
- ❌ **Cache API**: Designed for HTTP responses (overkill, less control)

**Current Architecture Issue**:
```typescript
// frontend/src/store/upload-store.ts:190-198
export interface UploadedFile {
  id: string;
  documentId?: string;  // Supabase document ID
  file: File;           // ❌ Lost after upload completes!
  preview: string;      // ❌ Lost after upload completes!
  status: 'uploading' | 'ready' | 'processing' | 'error' | 'complete';
  progress: number;
}
```

**Why File Object Is Lost**:
- Upload store is session-scoped (resets on page refresh)
- File object is NOT serializable (cannot be stored in LocalStorage/SessionStorage)
- Zustand persist middleware only saves `settings`, not `files` array

**Proposed Solution**: Cache PDF as Blob in IndexedDB immediately after upload, retrieve on demand.

  documentId: string;
  blob: Blob;

export class PDFCacheService {
  private db: IDBDatabase | null = null;
  private dbName = 'hdav2-pdf-cache';
  private dbVersion = 1;
  private storeName = 'pdfs';

  // Initialize IndexedDB connection
  async init(): Promise<void>;

  // Cache a PDF blob
  async cachePDF(documentId: string, file: File, version?: string): Promise<void>;

  // Retrieve cached PDF blob
  async getCachedPDF(documentId: string): Promise<Blob | null>;

  // Check if cached PDF is valid (not stale)
  async isCacheValid(documentId: string, serverVersion?: string): Promise<boolean>;

  // Delete specific cached PDF
  async clearCache(documentId: string): Promise<void>;

  // Delete all cached PDFs
  async clearAllCache(): Promise<void>;

  // Get cache statistics
  async getCacheStats(): Promise<CacheStats>;

  // List all cached document IDs
  async listCachedDocuments(): Promise<string[]>;

  // Evict least recently used PDFs to free space
  private async evictLRU(bytesNeeded: number): Promise<void>;

  // Handle quota exceeded errors
  private async handleQuotaExceeded(bytesNeeded: number): Promise<void>;
}

// Singleton instance
export const pdfCache = new PDFCacheService();

#### 2. Documents Service Integration

**File**: `frontend/src/services/documents.ts`

**Change Location**: Lines 229-276 (getDownloadUrl method)

```typescript
// Get document download URL - try cache first, then backend/Supabase
async getDownloadUrl(id: string): Promise<string> {
  try {
    // ✅ NEW: Check IndexedDB cache first
    const cachedBlob = await pdfCache.getCachedPDF(id);

    if (cachedBlob) {
      // Cache HIT: Use cached blob
      console.log(`[PDFCache] Cache HIT for document ${id} (${(cachedBlob.size / 1024 / 1024).toFixed(2)} MB saved)`);
      return URL.createObjectURL(cachedBlob);
    }

    // Cache MISS: Fetch from backend
    console.log(`[PDFCache] Cache MISS for document ${id}, fetching from server...`);

    // Try to get document info from FastAPI first
    const response = await fetch(`${API_BASE_URL}/api/documents/${id}`, {
      method: 'GET',
      headers: { 'Content-Type': 'application/json' }
    });

    if (response.ok) {
      const doc = await response.json();

      // Fetch PDF blob from backend
      const pdfResponse = await fetch(`${API_BASE_URL}/api/documents/${id}/download`);
      if (pdfResponse.ok) {
        const blob = await pdfResponse.blob();

        // ✅ NEW: Cache the downloaded PDF for future use
        try {
          await pdfCache.cachePDF(
            id,
            new File([blob], doc.original_name, { type: 'application/pdf' }),
            doc.updated_at
          );
          console.log(`[PDFCache] Cached document ${id} for future loads`);
        } catch (cacheError) {
          console.warn('[PDFCache] Failed to cache downloaded PDF:', cacheError);
        }

        return URL.createObjectURL(blob);
      }
    }
  } catch (error) {
    console.warn('[PDFCache] Cache retrieval failed, trying Supabase...', error);
  }

  // Fallback to Supabase (existing code)
  try {
    const { data: doc, error } = await supabase
      .from('documents')
      .select('storage_path, original_name, updated_at')
      .eq('id', id)
      .single();

    if (!error && doc?.storage_path) {
      const { data: urlData, error: urlError } = await supabase.storage
        .from('documents')
        .createSignedUrl(doc.storage_path, 3600, {
          download: doc.original_name
        });

      if (!urlError) {
        // ✅ NEW: Fetch and cache the PDF from Supabase
        const pdfResponse = await fetch(urlData.signedUrl);
        const blob = await pdfResponse.blob();

        try {
          await pdfCache.cachePDF(
            id,
            new File([blob], doc.original_name, { type: 'application/pdf' }),
            doc.updated_at
          );
          console.log(`[PDFCache] Cached document ${id} from Supabase`);
        } catch (cacheError) {
          console.warn('[PDFCache] Failed to cache Supabase PDF:', cacheError);
        }

        return URL.createObjectURL(blob);
      }
    }
  } catch (error) {
    console.warn('Supabase storage not available');
  }

  // If all else fails, return empty string
  console.warn(`Unable to get download URL for document ${id}`);
  return '';
}
```

## Notes

### Why IndexedDB Over Other Solutions?

**Comparison Table**:

| Storage Option   | Capacity | Persistence | Async  | Blob Support | Verdict      |
|------------------|----------|-------------|--------|--------------|--------------|
| LocalStorage     | 5-10 MB  | Persistent  | ❌ Sync | ❌ No        | ❌ Too small |
| SessionStorage   | 5-10 MB  | Session     | ❌ Sync | ❌ No        | ❌ Too short |
| IndexedDB        | 50+ MB   | Persistent  | ✅ Async | ✅ Yes       | ✅ Perfect   |
| Cache API        | 50+ MB   | Persistent  | ✅ Async | ✅ Yes       | ⚠️ Overkill |

**Why NOT Cache API**:
- Designed for caching HTTP responses (Service Worker pattern)
- Requires URL-based keys (we need document ID-based keys)
- More complex to implement
- IndexedDB gives us more control over storage/eviction

### Browser Compatibility

**IndexedDB Support**:
- Chrome: ✅ v24+ (2013)
- Firefox: ✅ v16+ (2012)
- Safari: ✅ v10+ (2016)
- Edge: ✅ All versions

**Private Browsing Mode**:
- IndexedDB disabled or limited in private browsing
- Graceful fallback: Direct fetch (no caching)
- No error shown to user (seamless degradation)

### Security Considerations

**Data Privacy**:
- PDFs cached in user's browser only (not shared across devices)
- IndexedDB is origin-scoped (isolated per domain)
- No sensitive data in cache metadata (only document ID, filename, size)

**Cache Invalidation**:
- Version tracking ensures stale cache detected
- User can manually clear cache (browser settings or app settings page)
- Cache purged when browser data cleared
