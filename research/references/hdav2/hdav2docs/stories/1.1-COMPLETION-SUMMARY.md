  - `pgmq` v1.4.4 (message queue)

### 2. Connection Method (CRITICAL)

**Working Solution**: Session Pooler (Port 5432)

```
postgresql://postgres.axxqiiszvdtialoxwkul:{PASSWORD}@aws-1-us-west-1.pooler.supabase.com:5432/postgres
```

**Why Session Pooler?**
- pgmq requires long-lived connections
- Transaction Pooler (Port 6543) uses connection pooling incompatible with pgmq
- Session Pooler maintains persistent connections needed for queue operations

**Why Not Direct Connection?**
- Supabase only provides IPv6 connectivity for direct connections
- Our environment doesn't support IPv6
- **Solution**: Use pooler instead (IPv4 compatible)

## Critical Learnings & Documentation

### For Future Development

1. **ALWAYS Use Session Pooler for pgmq**
   ```
   Port 5432 (Session Pooler) ✅
   Port 6543 (Transaction Pooler) ❌
   ```

2. **Connection String Format**
   ```
   postgresql://postgres.{PROJECT_REF}:{PASSWORD}@aws-1-{REGION}.pooler.supabase.com:5432/postgres
   ```

3. **IPv6 Limitation**
   - Direct connection requires IPv6
   - Use pooler for IPv4 environments
   - Pooler provides same functionality without IPv6 requirement

4. **Schema Deployment**
   - Must explicitly set `search_path TO public;`
   - Use `IF NOT EXISTS` for idempotent deployments
   - Deploy via Supabase SQL Editor for best results

5. **Environment Variables**
   - `DATABASE_URL` must point to Session Pooler
   - `SUPABASE_SERVICE_KEY` for backend operations
   - `SUPABASE_ANON_KEY` for frontend operations
